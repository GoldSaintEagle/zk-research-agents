# 密码学论文写作手册（中文摘要）

英文主入口：[paper-playbook](../../skills/paper-playbook/SKILL.md)。
逐节指南位于 `sections/`；专门技能包括 abstract-craft、technique-overview、
related-work-writing、experiments-writing 和 polish-writing。
公开论文只用来分析组织方法；玩具示例明确标为虚构，不提供可引用的科学结果。

## 从参考论文到本文章节

将摘要的“内容—功能—依赖”方法扩展到全文，但不把长章节机械地逐句打标签。
先核读参考论文的实际段落，理解它在解释什么、为何放在此处、依赖哪些定义，
以及为下一段提供了什么。遇到术语首次出现、代词指向或多重论断不清时，再拆到句子。

参考记录：
`来源与版本 | 章节/页码和段落定位 | 内容 | 功能 | 前提 | 后续需要的信息 | 可借鉴之处及限制`。

本文大纲：
`单元 | 读者问题/功能 | 已有前提 | 具体内容 | claim/evidence/来源 | 后续依赖 | 实质边界`。

完整重写时将大纲保存在 `paper/SECTION_PLAN.md` 或现有同类文件；小改复用既有大纲。
大纲之后继续完成用户已授权的写作，无需额外要求用户批准大纲。只修改 skill 时不自动改论文。
英文方法见 [section-planning.md](../../skills/paper-playbook/references/section-planning.md)。

## 来源与术语

- 优先核读相关已发表原始论文，也读用户指定的参考。Nova 示例采用 CRYPTO 2022 发表版；
  HyperNova 示例实际采用扩展版，不能把其额外章节说成会议版；Quasar/KiloNova 按预印本标注。
  版本与链接见 [source-corpus.md](../../skills/paper-playbook/references/source-corpus.md)。
- 引言、贡献、概览和相关工作的段落功能分析见
  [front-section-patterns.md](../../skills/paper-playbook/references/front-section-patterns.md)；
  定义、构造、证明、评测与附录见
  [formal-section-patterns.md](../../skills/paper-playbook/references/formal-section-patterns.md)。
  观察到的写法与推荐的大纲分开记录，不能把单篇论文的结构当成通用规定。
- 同一概念有多个等价称呼时，优先使用所核读的相关独立论文中多数共同采用的词，并优先考察已发表版本。
  一篇使用 A、其余使用等价的 B 时默认选 B；不能因为 A 来自名篇或用户指定文献就优先采用。
- 比较实际定义与安全模型，按独立作品判断使用情况，不统计搜索命中或同一论文的多个版本。
  少量相关论文不能支持“全领域多数”的断言；没有共识时使用准确的普通描述或明确归因的词。
- 原文引用、不同定义、专用算法名和必要的 API/transcript 标识符按需保留。
  先说明陌生对象代表什么、检查什么或计算什么，再让名称承担论证。不要为普通步骤创造新名字或缩写。
  完整规则见 [terminology.md](../../skills/paper-playbook/references/terminology.md)。

## 符号优先沿用已有论文与 baseline

- 对定义相同的对象，尽量使用此前相关论文的符号，尤其是直接 baseline 的记号，
  方便读者对照公式、算法和成本。先核读原文定义，核对对象、类型、取值域、维度和参数意义。
- 以 baseline 的符号体系为起点，保持一套一致的约定；不同参考文献发生冲突时不要随意混用。
  如采用更通行的领域记法更清楚，可以调整，但应说明对应关系。
- 尽量保持域/群、实例/见证、规模/次数参数、上下标、向量/矩阵及运算符的记法一致，
  不为体现“新颖性”或文字美观而换字母、换名称。
- 仅在定义确有不同、符号冲突、类型或取值域不兼容等情况下作必要调整；改动尽量小，
  首次使用时定义，并在预备知识或相关定义附近说明与原文/baseline 的对应关系。
  不能为了外观一致把不同概念写成同一符号。
- 在现有 NOTATION 表中按需记录“来源论文/章节、原符号、本文符号、含义/类型/域、改动理由”；
  正文、算法、图表和附录采用一致约定。忠实引用保留原符号，转换引用定理的记法时说明映射。
- 单纯语言润色不擅自替换数学符号；获授权进行符号修改时，按映射统一检查公式、量词和假设，
  避免无上下文的全文替换。详见英文 [notation alignment](../../skills/paper-playbook/references/terminology.md#align-notation-with-prior-work-and-the-baseline)。

## Preliminaries：一般定义、符号与具体参数分开

- Preliminaries 以独立的 `\subsection{Notation}`（符号约定）开头；此处是 **Notation**，
  不是表示安全概念的 Notion。说明后文实际使用的群、域、运算、单位元、生成元、
  instance/witness、向量/矩阵、指标、规模和次数等记号，并给出类型与取值域。
- 符号优先与定义等价的已有论文及 baseline 一致。例如适用时可用 $\mathbb G$ 表示
  阶为素数 $r$ 的加法群，以 $\mathbb F_r$ 表示 scalar field；椭圆曲线情形还需区分
  base field $\mathbb F_p$、曲线群和所用子群。这只是一般示例，不强制所有论文采用同一字母或假设。
- 本节讲一般对象、接口和符号参数，不给出实验所选的具体数值。具体曲线/域选择、模数、
  位宽、容量、arity、轮数/查询次数和工作负载规模放到实验/评测部分，再与本节符号逐项对应；
  不以实现参数表开篇，也不把具体取值反复嵌入背景定义。
- 理论成立所必需的条件仍放在相关定义或定理附近，例如群阶/特征限制、次数与域大小关系、
  容量不等式及安全模型/假设。移走具体取值不等于移走定理前提，也不禁止公式中的数学常数。
- 一般符号不代表已证明一般性。若只核验了固定实例或具体哈希，必须保留这一适用范围，
  并指向后文的实例选择；不能把常数改成自由变量就宣称适用于任意参数。
- 实验部分说明各取值的来源、适用条件，以及该配置是实际测量、仅作计数还是仅被定义。
  纯理论论文不强加实验；确有具体示例时放在后面的实例化/成本分析小节。

详见 [Preliminaries 指南](../../skills/paper-playbook/sections/07_preliminaries.md#general-setting-and-the-notation-subsection)。

## 不可因写作而改变的内容

1. 本文科学陈述只使用 survived 或按原有限定表述的 weakened claims。
2. 本文数值结果可追溯到 EVIDENCE；区分测量、运算计数、估计、构造性上界和引用数据。
3. 保留定理的量词、模型、setup、假设、提取器资源和误差界。
   局部收益不等于总成本改进，组件证明不等于完整 SNARK、零知识或具体安全等级。
4. **除非正式证明很简单，否则完整正式证明默认放入对应附录。** 正文保留完整定理陈述、
   实质假设和简短且明确标为 **Proof sketch** 的证明思路，并明确说明完整证明位于哪个附录小节。
   例如：`The complete proof appears in Appendix~\ref{app:proof-main}.` 附录反向引用对应定理。
   不能把“放到附录”当成已经证明，也不能隐藏改变结论的前提。
5. 不因模板缺一项而编造开放问题、统一框架、推广、实验、最终编译或 artifact。

## 全文组织与页数

按信息依赖安排顺序，可以合并相关工作与引言，也可以把每个构造和对应定理放在一起。
理论论文不强制有实验节；实现论文要核查实现改动是否改变沿用的安全前提；
应用/电路论文应较早说明待证关系和信任边界。不固定章节占比、贡献条数或段落数。

根据适用年份 CFP 和用户约束，分别记录正文、参考文献、附录及补充材料的页数规则。
参考文献和附录不计入正文时分别计数，但不因此推断附录不限页。
先删重复叙述，再处理版面；遵守模板字号、页边距和间距，不用负间距强塞内容。
修改版面后检查实际 PDF。未知规则保留为未知，不继承其他年份的限制。

## 标题从已建立的结果出发

- 标题优先回答“本文得到了什么结果”，突出构造的已证性质、效率改进、复杂度界或安全保证，
  而不是只写研究对象或待解决的任务，如仅写 “Checking …”。分析型论文也可以突出已证下界、
  局限或资源 trade-off；从结果出发不意味着一定要宣称性能提升。
- 可采用 `Efficient [对象/操作]`、`[对象] with Constant [资源]`、`[对象] with [已证保证]`
  等形式。它们是可选结构，不是必须添加的形容词；关键是让结果成为标题的主要信息。
- `Efficient`、`Faster` 或降低成本必须有具体指标、比较对象、参数范围和理论/实验依据。
  仅减少一种 primitive operation 时应明确指标，不能据此声称整体运行时间或完整系统更高效。
- `Constant` 必须明确恒定的是哪个资源、相对于哪个变化参数，以及对安全参数等量的依赖。
  一个固定实验点不构成渐近常数界；常数群操作、proof size、storage 与完整验证成本不能互换。
- 标题保留会影响结论理解的条件性、适用域和比较范围。若缺少效率或常数性质，就使用已建立的
  保证、界或代价权衡，不为迎合标题而扩大结论，也不把强主张藏入副标题。
- 候选标题记录“标题、核心结果、claim/theorem/evidence、必要限定、可能误读”；候选不等于已选定。
  用户已授权改标题时继续完成，无需额外审批。应用后检查 PDF 排版及投稿文本是否一致。

详见 [标题指南](../../skills/paper-playbook/sections/01_title.md#lead-with-the-established-result)。

## 限制应配套适用性论证

- 对 bounded depth、有限容量、受限关系、额外假设或组件实验等重要限制，不能只列出限制，
  还应解释哪些有用结果仍成立、适用于什么具体场景，以及为何该限制在那个场景可以接受。
  justification 必须有证据，不能为“保证贡献”而把设想包装成已实现的普适性或实用性。
- 在既有章节计划中记录：限制及量词、影响的保证、适用工作负载、可接受的理由、缓解/转换方法、
  正确性条件、额外成本/假设、定理或证据来源、剩余缺口。没有现成证据时标为待验证扩展。
- 在引言/贡献旁给出简短理由，在构造中说明转换接口，在安全部分核对前提与误差/资源界，
  在实验中计入增加的电路、prover、内存、通信和 setup 成本。避免重复泛泛的限制声明。
- bounded height 是高度上限，不一定是固定执行步数。区分执行依赖图、证明聚合图与展开的
  extraction tree，也区分每节点 folding arity 和整层 width。
- 对能正确组合的 $n$ 个分段 claim，理想平衡 $q$ 叉聚合树（$q\ge2$，叶高为零）高度为
  $\lceil\log_q n\rceil$。增加 arity 可以减少聚合层数，但固定 $q,d$ 最多容纳 $q^d$ 个叶子；
  更大输入需要增大参数或单节点工作量，不能据此宣称固定配置支持任意规模。
- 加宽原计算图不能自动消除顺序依赖；但顺序 trace 已生成后，分段证明可能通过浅层树聚合。
  这需要证明分段边界、顺序、程序及状态/内存一致性，而非仅折叠各自有效的 instance。
  聚合深度降低不等于原始 trace 可以并行生成。
- 通过加宽、分块或增加局部电路降低递归深度时，必须重新核对容量、成本、提取时间和安全损失。
  “每个有限输入都可选更大参数”不等于“固定参数覆盖任意计算”。明确区分已证适用性、
  条件性扩展和未解决限制；外部系统实例也不能替代本文的构造与证明。

详见 [limitations and applicability](../../skills/paper-playbook/references/limitations-and-applicability.md)。

## 各节功能大纲

| 部分 | 建议的信息推进 | 需要避免的误用 |
|---|---|---|
| 标题 | 已建立的结果/性质 + 熟悉的研究对象 + 必要范围 | 只写待解决任务、无依据的 Efficient/Constant、强制品牌或夸大安全性质 |
| 引言 | 任务与对象 → 已有路线 → 具体障碍 → 本文结果与范围 → 阅读入口 | 强制领域漏斗、编号目标式或“长期开放问题” |
| 贡献 | 可辨别的结果 → 条件与意义 → 正文或证据位置 | 固定三四条、重复拆分一项贡献、把局限移走造成过度承诺 |
| 技术概览 | 所需对象 → 关键操作 → 为什么有效 → 组合与适用边界 | 强制“问题—Insight”、空有名称、没有根据的统一框架 |
| 相关工作 | 共同问题/比较维度 → 原文方法及条件 → 本文具体差异或互补性 | 固定段数、硬凑对立路线、把不可比指标放在同一排名 |
| 预备知识 | 直观作用 → 类型和定义 → 所需接口/性质 → 后文用途 | 未使用的大段教程、符号先用后定义、把本文新对象当标准定义 |
| 主构造 | 目标关系和接口 → 对象与状态 → 操作和验证条件 → 输出 → 性质及成本 | 强制 PIOP–PCS–FS 链条、遗漏挑战顺序、把部件称作完整系统 |
| 安全与正确性 | 完整定理与前提 → 简短 proof sketch → 对应附录的完整证明；简单证明可直接留正文 | 缺失的 ZK 证明、把假设当定理、无预算的安全位数、没有明确附录指向 |
| 评测 | 待回答的问题 → 配置和比较口径 → 方法 → 证据 → 原因解释及代价 | 固定九段、强制消融结论、把部分运算节省说成完整运行时间提升 |
| 结论 | 已建立的答案 → 适用范围和意义 → 必要的后续问题 | 机械重复全文、引入新结果或夸大可用性 |
| 附录 | 对应正文定理 → 非简单结果的完整正式证明 → 精确双向引用 | 隐藏前提、与正文定理不一致、将附录默认视为不限页 |

这些是读者需要获得的功能，可合并、拆分或按实际结果省略；不会自动变成同名小节。
每节写前先查对应英文指南，写后检查对象首次解释、逻辑依赖和证据路径。

证明是否“简单”按实际论证判断：由已有定义或引理直接推出的简短推导可留在正文；
涉及较多分类讨论、hybrid、递归提取或长篇技术推导时，完整证明放附录。不能通过删步骤或写
“标准可得”把复杂证明伪装成简单证明。Proof sketch 只保留关键思路，不重复完整推导。
如实际会议规则明确要求不同放置方式，记录该例外。“Formal proof”在此指完整数学证明，
不自动表示已完成 Lean 等机器形式化。

**摘要（按句子功能组织）**：
- 先核读指定参考摘要并逐句记录内容、作用和信息依赖。Quasar 从具体瓶颈进入，依次给出定义、带边界的结果、机制、组合和应用；KiloNova 从应用收窄到缺口，再介绍贡献类型、核心技术、PCD、最终编译及评价。借鉴结构，不移用它们的技术主张。
- 通用大纲：背景与对象 → 具体问题及口径 → 本文贡献类型 → 对具体对象执行的核心操作 → 实际组合或条件性保证 → 有口径的证据与代价 → 结论及必要边界。先让读者知道对象和作用，再使用陌生名词或缩写。
- 不固定七句或三段，不强制制造“开放问题”、框架名、视角、实验、最终 SNARK 或 artifact。先在 ABSTRACT_PLAN 中逐句对应功能、前提、内容、claim/evidence 和边界，再按用户已授权的任务完成正文。
- 保留模型与知识假设，区分计数/上界/测量、组件/完整系统、局部收益/总成本；单篇有出处不等于术语通行。不照抄参考摘要中的“最先进”“实用”等性能形容词。
- LaTeX 与纯文本摘要保持同一内容，运行证据审计并检查实际第一页排版；不要通过改字号、页边距或负间距强塞。英文流程及逐句示例见 `skills/abstract-craft/SKILL.md` 和 `references/sentence-functions.md`。

## 清晰表达、连续推导与贡献取舍

以下规则适用于摘要、正文、图表说明和附录。英文统一规则见
`skills/paper-playbook/references/clear-exposition.md`。

- 每句话聚焦一个主要问题。不同问题、转换步骤和实现障碍分别解释；只有简单且联系明显的内容才合并。分号不能代替缺失的说明，也不设置机械字数上限。
- 先说明具体检查的对象和操作，再讲所用方法。例如先说明 commitment 的 random linear combination 检查，再解释群等式怎样变成多项式检查，最后引出该方法在递归电路中的基域/标量域运算问题。区分线性组合的权重与证书多项式的系数。
- 按 A → 操作 → B → 后续结论或障碍 → C 连续展开。新对象、新问题应从刚解释的内容接入；独立分支明确说明转向及其相关性，不虚构因果联系。不能只说“转成多项式”而不解释中间表示及其成立原因。
- 摘要保留理解机制所需的关键桥接步骤；技术概览解释中间对象，正式构造给出方程和条件。篇幅不足时先删次要实现细节，不删掉必要的逻辑连接。
- 普通 commitment、先承诺后挑战、Fiat–Shamir、常规编码和直接使用标准 sumcheck，不因被使用就成为贡献，也不应在摘要、引言中反复突出。若整合确有新意，应明确新增的性质、定理或收益及证据。
- 适合时先描述交互式协议，再简短说明通过 Fiat–Shamir 得到非交互版本，标明适用模型并指向安全分析。具体 transcript 顺序、绑定、域分离和编码保留在协议定义或对应附录。简化介绍不等于无条件证明 FS 安全；固定哈希或递归所需的额外假设仍须明确。

## 润色与交付

润色先确认段落的作用和输入/输出信息，再删冗余；句子短不等于逻辑清楚。
保留安全术语的语义区别，能由正式定义确定的措辞错误按授权修正并记录，
无法确定时保留疑点并询问所缺信息，不因碰到技术词就一律要求批准。
重大内容修改由独立审查复核；编译和数值审计适用于实际论文修改。
技能维护则检查路径、同步副本、指令冲突和实际使用行为，不把它宣称为新的论文安全审计。

## 配套流程

- 模拟审稿（`skills/mock-review`）：投稿前 3 天与前 1 天各一轮；先写可证伪清单，派"专家怀疑者 / 通才 / 实现者"（可加数据审计、桌拒审计）优先推翻；主 agent 逐条核实，只接受能在源码、数据或脚本中定位的发现；输出评分与"必改 / 建议 / 不改"修改清单，并列出已核对无误的部分。
- 答辩（`skills/rebuttal`）：拆分原子问题 → 分类（必答 / 澄清 / 认错并修 / 承诺 / 忽略）→ 先写内部详版再压缩为提交版（常见目标 500–700 词）→ 答案先行、证据其次、改动第三 → 把质疑转化为论文新内容 → 主动撤回站不住的数字。
- 匿名检查（`skills/anonymize-check`）：`anon_check.py` 扫描源码、PDF（文本、元数据、嵌入路径、压缩对象流）、补充材料与制品。
- 定稿（`skills/camera-ready`）：页数计数口径、版权表单、作者变更政策、全版发布、0 个未定义引用、字体全部嵌入、无明显 overfull、无叠印。
